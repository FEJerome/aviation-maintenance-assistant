# ADR-006：流式场景下段落级增量 Markdown 渲染

- **状态**：Accepted
- **日期**：2026-06-09
- **决策者**：马昊宇（项目作者）

---

## 背景

当前系统的流式输出链路已经跑通（SSE + TokenStream + 前端 ReadableStream），但 Markdown 渲染策略是"complete 后一次性渲染"。这带来了路演级别的体验问题：

1. **流式过程中的 raw markdown 暴露**：用户先看到 `**发动机检查**：必须参考**Rotax912...` 长达 5~10 秒，complete 后才突然变成漂亮格式
2. **"先丑后美"的闪烁感**：面试/路演场景下，这种视觉跳跃显得不专业
3. **内容与格式脱节**：如果 LLM 输出 20 秒，用户前 19 秒看到的都是不可读的标记符号

本决策需要确定：**在流式输出场景下，如何在保证格式正确性的前提下，尽早将已生成的内容渲染为漂亮格式**。

## 考虑的选项

### 选项 A：逐 token 实时渲染（B1）

**实现方式**：
- 每收到一个 token，将当前完整 buffer 传给 `marked.parse()`
- 用 `v-html` 直接替换整个消息的 DOM

**优势**：
- 理论上是"最实时"的方案，每字都是格式化后的
- 代码最简单：直接 `buffer += token; html = marked.parse(buffer)`

**劣势**：
- **DOM 剧烈抖动**：Markdown 是上下文敏感的，未闭合的标签会导致整棵树重建。例如 `## 检查步骤` 在收到 `1` 后变成 `<h2>检查步骤1</h2>`，后续内容追加后又变回 `<p>## 检查步骤1...</p>`
- **性能灾难**：每秒 5~20 次 full re-render，CPU 占用飙升
- **布局跳动**：滚动条、光标位置、图片尺寸都会频繁变化，体验极差
- **工程不可行**：除非重写 marked.js 的增量解析器（1~2 个月），否则当前技术栈无法稳定支持

### 选项 B：段落级增量渲染（B2）

**实现方式**：
- 前端维护两个 buffer：
  - `confirmedBlocks`：已确认的稳定段落，用 `marked.parse` 一次性渲染为 HTML
  - `streamingBuffer`：正在流式接收的内容，以纯文本形式显示
- 每次收到 token 后，调用段落边界检测算法（`findParagraphBoundary`）
- 一旦检测到段落边界（如 `\n\n`、代码块闭合、列表项切换），将 completed 部分固化到 `confirmedBlocks`，剩余部分留在 `streamingBuffer`
- Vue 模板用 `v-for` 渲染 `confirmedBlocks`，用 `{{ streamingBuffer }}` 显示当前累积内容

**优势**：
- **稳定性高**：只有"已确认的完整段落"才渲染 Markdown，不会出现未闭合标签
- **效果好**：观众看到"段落逐步绽放"的效果，每完成一段就立即格式化
- **性能可控**：渲染频率从"每 token"降到"每段落"（通常每段 2~10 秒渲染一次）
- **工程落地周期短**：2~3 天可完成，不需要重写 marked.js
- **技术深度足**：涉及状态机、段落边界检测、双 buffer 同步等工程能力

**劣势**：
- **实现复杂度高于一次性渲染**：需要写段落边界检测逻辑和状态机
- **LLM 不换行时的退化**：如果 LLM 输出 500 字都不换行，`streamingBuffer` 会累积很长，需要兜底策略（最大长度强制分割）
- **已固化段落无法被后续 token 修正**：一旦段落被确认，后续 token 不会更新它（但流式 LLM 通常顺序生成，极少回头修改）

### 选项 C：隐藏中间态（B3）

**实现方式**：
- 流式过程中不显示任何内容，只显示一个"正在生成..."的打字机动画
- complete 后一次性渲染 Markdown

**优势**：
- 实现最简单，风险最低
- 用户看不到 raw markdown

**劣势**：
- 失去了流式输出的核心体验价值——逐字感知的低延迟
- 观众只能干等 5~10 秒，像在看一个 loading 动画
- 无法体现"流式输出"的技术亮点

## 决策

**采用选项 B：段落级增量 Markdown 渲染。**

**具体实施参数**：
- 两段式阈值设计：0~170 字符自由累积，170~200 字符进入急切模式（遇非列表序号的句末句号即分割），超过 200 字符兜底硬切。
- 段落边界仅由空行（`\n\n`）、代码块闭合、列表项切换触发；单个换行符不触发分割。
- 在 system prompt 中明确禁止 LLM 使用 `#` 标题，改用 `**加粗**` + 空行表示章节，从源头避免标题与正文混排的解析灾难。
- 增量渲染默认全局开启，保留配置开关支持一键退化为 complete 后一次性渲染。

核心判断依据：路演需要在"技术亮点展示"和"体验稳定性"之间取得平衡。选项 A 理论最完美但工程不可行；选项 C 最稳定但失去了流式的核心价值；选项 B 在可落地的前提下，实现了"段落逐步绽放"的专业效果，同时避免了逐 token 渲染的抖动问题。

## 后果

### 积极影响

- 路演展示效果大幅提升：观众看到的是"打字机效果 → 段落绽放 → 打字机效果 → 段落绽放"的节奏，比"打字机效果 → 突然全部格式化"更有品质感
- 系统架构演进：为后续更复杂的流式交互（如增量代码高亮、增量表格渲染）打下基础
- 技术面试谈资：可以深入讲解"为什么不用逐 token 渲染"、"段落边界检测的状态机设计"、"双 buffer 的同步策略"等工程细节

### 消极影响 / trade-off

- `ChatMessage.vue` 组件复杂度上升，从单一 `content` 变成 `confirmedBlocks + streamingBuffer`
- 需要维护段落边界检测算法的准确性，未来 LLM 输出格式变化时可能需要同步调整
- 如果 LLM 长时间不输出换行且句末句号稀少，buffer 可能在 170~200 区间停留较久，用户体验暂时退化到"纯文本累积"模式（两段式阈值和兜底策略可缓解）
- 已固化段落无法被后续 token 修正（流式 LLM 通常顺序生成，极少回头修改）
